我们先为项目添加了一项小功能，但更复杂的更改需要更完善的流程。GitHub Copilot app 支持组织现有的工作流，帮助我们用正确的方法构建所需功能。从本课开始，你将通过几节课遵循典型的智能体驱动开发流程：先使用 issue 实现新功能，确认代码有效且功能行为符合预期，最终将更改成功合并到项目中。

> [!NOTE]
> 后续功能工作流将沿用同一个会话。通常，不同类型的文件会使用不同会话或 PR；这里会采用简化方式，以便专注于核心概念。

在本课程中，你将：

- 从 GitHub issue 启动新的智能体会话。
- 在 **Plan** 模式中确定需求。
- 使用 **Autopilot** 模式实现新功能。
- 审查代码。
- 在浏览器画布中手动验证功能。

继续实现该功能时，你还将更新存储库指令、自定义现有的 quality-checks 技能、添加 MCP 验证、创建 QA 智能体并创建功能 PR。

## 场景

Tailspin Toys 的目录不断扩大，访问者需要按类别和发行商筛选游戏。待办事项中的 issue 已描述这项功能，但在编写代码前，需要先确认组合筛选等细节。你将使用 Plan 模式确定这些细节，然后授权智能体在明确范围内实现功能。

## 背景

将 AI 编码智能体引入开发流程，并不会改变软件开发的基本原则；这些原则反而变得更加重要！大多数开发人员的工作流程大致如下：

1. 打开描述所需工作的 issue。
2. 规划需要构建的内容。
3. 编写并审查代码。
4. 运行测试验证代码。
5. 手动验证新功能。
6. 创建拉取请求 (PR)。
7. 代码通过审查且持续集成流程成功后，合并代码。

> [!NOTE]
> 具体流程因团队和组织而异，但大多数流程都与上述方式类似。

遵循这种标准流程，可以确保 AI 生成的代码符合既定要求，并像手写代码一样经过审查。

## 会话模式

**会话模式**控制智能体的自主程度。可以在提示框下方的下拉列表中设置模式，并随时更改：

- **Interactive**：你与智能体协作。智能体提出更改建议，并等待你的输入后再继续。
- **Plan**：智能体先制定计划。你审查并批准计划后，智能体才会执行。
- **Autopilot**：智能体完全自主工作，包括编写代码、运行测试和迭代，无需等待输入。

先在 Plan 模式下审查计划，然后使用 Autopilot 实现计划。

## 从 issue 启动会话

开始前，确认星级评分 PR 已合并，并且本地 `main` 已更新。

1. 在侧边栏的 **Sessions** 下，选择 Tailspin Toys 存储库文件夹，然后在存储库顶部导航中选择 **Issues**。打开 **Allow users to filter games by category and publisher**。这是模板创建的现有 issue，无需另建。
2. 选择 **New session**，并选择基于更新后 `main` 的 **new working tree**。

    ![GitHub Copilot app 的 issue 视图，箭头指向 New session 按钮](../../../_images/app-new-session-from-issue.png)

3. 确认 issue 已附加到会话，并在模式选择器中选择 **Plan**。

> [!NOTE]
> 如果找不到 Node.js 或 npm，请让智能体运行 `node --version` 和 `npm --version`。如果这些命令在终端中有效，但在会话中无法运行，请检查应用的 PATH 或版本管理器设置，然后完全退出并重新打开应用。重试失败的操作和检查；不要仅因智能体找不到 npm 就重新安装 npm。

## 规划筛选功能

规划让你能在 Copilot 编写代码前审查方案。由于会话从 issue 启动，Copilot 已获得功能请求的上下文。发送：

```plaintext
Build this feature.
```

回答 Copilot 的问题，并对照 issue 的验收标准审查计划。确认计划涵盖类别和发行商筛选、无障碍控件、数据访问更改及测试。讨论尚不明确的行为，例如多个类别如何组合，或没有游戏匹配时如何处理。

计划应使用项目现有工具运行 lint、单元测试、E2E 测试和类型检查。将范围限定为筛选功能的实现和测试；完成质量工作流后再创建 PR。批准前请修改计划中不合适的内容，并保留 issue URL 和已达成共识的澄清信息，供后续验证使用。

## 明确批准 Autopilot

对计划满意后，选择 **Approve and implement this plan**，或当前版本中含义相近的选项。不要假定批准后会自动切换模式；确认模式指示器显示 **Autopilot**。

Copilot 会开始实现功能，按照既定计划迭代、生成代码并运行测试。

> [!NOTE]
> 批准后可能立即开始实现，因此请先审查计划。如果 Copilot 报告缺少依赖项或端口冲突，请先解决设置问题，再判断检查是否完成。只停止自己启动的服务器。

## 审查并验证实现

生成代码后，和其他代码一样，必须先审查再合并。现在审查代码并运行网站，确认一切正常。

1. 打开 **Changes**，检查筛选功能实现和测试。
2. 根据 issue 和批准的澄清信息审查结果，包括多类别及发行商组合。确认更改符合现有存储库指令。
3. 查看 lint、单元测试、E2E 测试和类型检查的输出。跳过的检查不能算通过。
4. 接受实现前，解决失败项并重新运行受影响的检查。Playwright 的 E2E 配置会构建并提供预览服务，而且可能复用本地服务器；确保被测服务器属于此工作树，而不是之前课程启动的服务器。

## 体验新功能

代码看起来没问题，但能否正常运行？像之前一样启动应用，并在浏览器画布中打开网站。

1. 使用以下提示，让 Copilot 启动应用并在浏览器画布中打开页面：

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. 稍等片刻，应用将启动，Copilot app 内会打开浏览器窗口。
3. 选择类别，确认显示结果符合该类别。清除筛选，再选择发行商，确认结果符合该发行商。
4. 同时应用类别和发行商筛选，并对照 issue 和已批准的计划检查结果。如果支持多个类别，还要验证约定的组合行为。
5. 测试没有匹配游戏的筛选组合并检查空状态。清除或重置筛选，确认完整列表重新显示。
6. 完成后，使用以下提示让 Copilot 停止为此会话启动的开发服务器并关闭浏览器画布：

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 将此会话保留到后续课程

暂时不要创建或合并筛选 PR。第 4 至第 8 课会继续使用此会话、工作树和分支。下一步先将自定义指令应用于筛选代码，然后添加技能和 QA 改进，最后在第 8 课中创建并合并合并后的 PR。停止开发服务器后，可以将会话留在空闲状态；下一课再返回同一个会话。
